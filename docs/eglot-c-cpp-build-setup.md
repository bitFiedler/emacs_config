# Eglot, clangd and C/C++ build configuration

This guide explains Eglot and clangd setup for C/C++ projects, with native and Docker workflows. **Preferred database methods: Bear for Make-based projects; CMake's `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON` for CMake projects.** Internal project deployment settings stay outside this repository.

## Who does what

| Component | Responsibility |
| --- | --- |
| C/C++ major mode and tree-sitter | Editing, syntax structure and local structural navigation |
| Eglot | Emacs LSP client: sends requests and displays server results |
| clangd | C/C++ parsing, semantic completion, definitions, declarations, references and diagnostics |
| Make / CMake / Kbuild | Actual build rules, compiler flags and generated files |
| Bear | Records executed compiler calls from a Make/custom-script build |
| `compile_commands.json` | Per-source compiler command, working directory, include paths and macros |
| Docker launcher | Runs clangd in the matching build container and maps file URIs |

Eglot does not infer a kernel configuration from the file name. clangd needs a compile command matching the file and build variant. Missing `-I`, `-D`, language or target settings can produce false diagnostics and incomplete navigation; see [clangd's explanation of compile commands](https://clangd.llvm.org/design/compile-commands). A header normally borrows a suitable source file's command. Compilation commands describe analysis; starting clangd does not itself compile/install the project.

## Basic Emacs connection

Install an Emacs version with Eglot support and install clangd where it will run (host or build container). In a plain Emacs configuration, a minimal TS-mode setup is:

```elisp
(require 'eglot)
(add-to-list 'eglot-server-programs
             '((c-ts-mode c++-ts-mode) . ("clangd")))
(add-hook 'c-ts-mode-hook #'eglot-ensure)
(add-hook 'c++-ts-mode-hook #'eglot-ensure)
```

For classic modes, add corresponding `c-mode` / `c++-mode` entries and hooks. Use the actual installed executable name, such as `clangd` or a versioned binary. This repository already configures Eglot: its users should use project-local overrides instead of duplicating global hooks. Choose a project root (a Git checkout provides one), prepare the database, open a source file and invoke `M-x eglot` if it did not start automatically.

The native demo directory settings start host clangd. The Docker settings start `python3` plus the repository's `my-docker-clangd.py` helper. Change the example's absolute-path placeholders to your checkout and launcher; retain the actual image tag, container mount and database directory used by that example. No internal registry or private source checkout is required.

## Configuration files and paths

| File/setting | Purpose |
| --- | --- |
| `.dir-locals.el` | Select the project-specific server command in Emacs |
| `eglot-server-programs` | Launcher command for the relevant modes |
| `.clangd` | clangd analysis adjustments, such as scoped GCC-only flag exclusions |
| `compile_commands.json` | Build information generated by Bear/CMake |
| Kernel `.config` and generated headers | Build-variant definitions needed for correct kernel analysis |
| `--host-root` / `--container-root` | Map the same checkout between editor and container paths |
| `--database` | Directory containing `compile_commands.json` inside the container, not the JSON filename |

Use the [generic examples](examples/eglot-build-databases/README.md) as a starting point. Keep the language override scoped to the C/C++ modes so Python/shell buffers retain their own servers. Do not copy one project's Docker paths or compiler exclusions blindly into another. clangd loads project `.clangd` files along source-directory ancestry; see [its configuration reference](https://clangd.llvm.org/config).

## Make-based projects: Bear preferred

Run the existing build command through Bear, without changing the real compiler:

```sh
bear -- make
# Explicit database location:
bear --output build/compile_commands.json -- make
```

Create the output directory first if it does not exist. Bear options precede `--`; the normal build command follows it. When the compiler is invoked through a build script, wrap that script instead, unless it already invokes Bear internally. If a project script already invokes Bear, do not nest another Bear wrapper around it.

Bear captures real compiler calls, not all possible Makefile rules. An incremental no-op build can yield no entries. For ongoing work with unchanged build configuration, `bear --append -- make` retains prior entries; after changing compiler/configuration, regenerate coherently instead of accumulating incompatible duplicates. These behaviors and options are documented in the [Bear 3 manual](https://github.com/rizsotto/Bear/blob/3.1.6/source/bear/man/bear.1.md). Check the installed `bear --help` when using another version.

For a first complete capture, use the project's normal build procedure that actually compiles the sources of interest. Do not prescribe a destructive clean or costly full kernel build merely to fix editor startup. A valid existing database can be reused. See the [Bear upstream repository](https://github.com/rizsotto/Bear) for other build-tool integrations.

Runnable original example: [Make demo](examples/eglot-build-databases/make-demo/Makefile). Copy the directory to a scratch checkout, run `bear -- make`, and inspect the database. `src/main.c` calls a function declared in a header and defined in `src/answer.c`, providing a small cross-file jump example.

## CMake projects: native export

Configure with the export option rather than wrapping CMake compilation with Bear:

```sh
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build
```

CMake writes `build/compile_commands.json` during configuration/generation. Building is still needed when headers or sources are generated by build steps. The export is supported by Makefile and Ninja generators, rather than all generators; see the [CMake variable reference](https://cmake.org/cmake/help/latest/variable/CMAKE_EXPORT_COMPILE_COMMANDS.html).

Point clangd at the build directory using the launcher `--database` setting or project configuration. The database must use paths available in the server environment. Runnable original example: [CMake demo](examples/eglot-build-databases/cmake-demo/CMakeLists.txt). For a larger open-source worked project, use the official [CMake tutorial and its downloadable source examples](https://cmake.org/cmake/help/latest/guide/tutorial/index.html), configuring its source with the same export option.

## Linux kernel specifics

See the [upstream Linux native/Docker walkthrough](examples/linux-kernel/README.md) for fresh public kernel checkouts, smaller/full Bear captures, Eglot configurations and the [kernel development Dockerfile](examples/linux-kernel/docker/Dockerfile).

For an already configured upstream Linux checkout, capture its normal Make build:

```sh
# Run from the Linux checkout, in the same environment as clangd.
bear --output compile_commands.json -- make -j"$(nproc)"
```

This executes a real kernel build. Preserve the actual target, architecture, toolchain and output-directory arguments your build requires; it is not necessary merely to reconnect Eglot.

Kbuild's include paths, generated architecture headers, `__KERNEL__`/configuration macros and chosen compiler target matter. Preserve the actual `.config`, generated headers and compiler environment. Files disabled by that configuration may have no captured command. A GCC-built kernel can be analyzed by clangd; only unsupported GCC options need scoped analysis exclusions. This does not justify switching the actual compiler or deleting defines/include paths.

As an optional fallback for an already built Linux tree, [Linux v6.12's database generator](https://github.com/torvalds/linux/blob/v6.12/scripts/clang-tools/gen_compile_commands.py) reads saved Kbuild `.cmd` records. Bear remains the preferred Make workflow. [Linux's LLVM build guide](https://docs.kernel.org/kbuild/llvm.html) explains `LLVM=1` when deliberately choosing a Clang/LLVM build; it is a separate choice from using clangd for editor services.

## Docker and Eglot startup

Generate the database and run clangd in the same container environment as the build. The Python helper selects exactly one running container by image and host bind mount, then runs `docker exec -i` without a TTY. The image is not a container name. The host/container mapping translates LSP file URIs, not arbitrary compiler options or missing filesystem dependencies.

Start the appropriate project container first. Confirm `clangd --version`, a nonempty database and accessible generated headers there. Apply the project's directory settings with `M-x normal-mode` and accept the reviewed local-variable prompt, then start `M-x eglot`. Stop an obsolete connection first; use `M-x my/eglot-reset-retries` if the personal ten-start budget has been exhausted.

For upstream Eglot instructions, use the [GNU Eglot manual](https://www.gnu.org/software/emacs/manual/html_node/eglot/index.html), also installed locally: `C-h i`, then `g`, enter `(eglot)` and press RET. [clangd's setup guide](https://clangd.llvm.org/installation) covers the language server side.

## Features and practical limits

| Action | Command |
| --- | --- |
| Definition | `M-.` |
| Declaration | `M-x eglot-find-declaration` |
| Type definition | `M-x eglot-find-typeDefinition` |
| References | `M-?` |
| Return | `M-,` |
| Completion | `M-TAB`, or the configured Company interface |
| Rename | `M-x eglot-rename` |
| Code actions | `M-x eglot-code-actions` |

The server must advertise the relevant feature. Reference/symbol coverage depends on available commands and index progress; inactive kernel variants and unbuilt files are not guaranteed complete. Eglot edits unsaved text through LSP, while generated headers and other unopened dependencies still need valid on-disk state.

## Troubleshooting by symptom

| Symptom | Check |
| --- | --- |
| Server exits immediately | Eglot stderr, Docker permissions, matching running container, executable/arguments |
| No matching container | Image tag and exact bind mount; start the correct project container |
| Multiple matches | Resolve duplicate project containers rather than selecting the first |
| Missing project headers | Database entry, include paths, generated files and working directory |
| Many unknown compiler flags | clangd compatibility; add only diagnosed scoped exclusions |
| Empty database | Whether the build actually executed compiler calls; Bear output directory and version |
| Wrong variant results | `.config`, architecture/sysroot, generated headers and stale/mixed database entries |
| Some definitions work, others do not | Database/index coverage and server diagnostics |

A nonzero standalone `clangd --check` result may include code-action self-tests as well as parsing failures; read its diagnostic lines rather than treating every status as a server-start failure. Check one representative source before broad changes. Build/database commands in this guide execute real builds unless explicitly described as inspection; no kernel rebuild was run to produce this documentation.

## Worked open-source project: cJSON

[cJSON](https://github.com/DaveGamble/cJSON) is a small public C project whose [upstream build documentation](https://github.com/DaveGamble/cJSON#building) describes both Make and CMake. The following commands adapt those build methods to produce clangd's database; they do not install the library into the system.

Use separate fresh checkouts so the workflows do not share stale object files:

```sh
git clone --depth 1 https://github.com/DaveGamble/cJSON.git cjson-make
cd cjson-make
bear -- make
```

Open a C file from that checkout in Emacs and connect Eglot to host clangd. Its database is in the checkout root. For the CMake workflow, start from another fresh checkout:

```sh
git clone --depth 1 https://github.com/DaveGamble/cJSON.git cjson-cmake
cd cjson-cmake
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build
```

Set `CompileFlags: CompilationDatabase: build` as nested YAML in a root `.clangd` file, as shown by the [native CMake demo](examples/eglot-build-databases/cmake-demo/.clangd), or start clangd with an absolute `--compile-commands-dir` pointing at that build directory. For Docker, clone/copy the public checkout on the host, bind it into the development container, and build/capture there using the same mount and launcher pattern as the Docker demos. Capture all compiler flags from the actual build rather than hand-writing include lists.

The cJSON command forms were checked against its upstream README and Makefile on 17 November 2026; no cJSON source is bundled here and these clone/build commands were not executed as part of the example checks. Upstream build requirements may evolve. The runnable original examples remain the small, dependency-free way to verify this workflow first.
